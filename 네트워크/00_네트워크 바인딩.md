# 00_네트워크 바인딩

> `127.0.0.1` 바인딩 vs. `0.0.0.0` 바인딩

어느 인터페이스로 들어오는 요청을 받을 것인가?

<br>

## 1. 리스닝

> 어플리케이션이 "리스닝"한다는 것의 의미

흔히 어플리케이션이 리스닝한다고 표현을 하면, 특정 포트에 대해서 리스닝 중이다라고 포트에 대해서 포커싱이 맞춰져 있는 것을 알 수 있다.

그러나 사실 리스닝의 정확한 의미는 **"이 IP 주소의 이 포트로 들어오는 요청을 받겠다"**로 IP에 대한 개념도 포함되어 있다.

<br>

## 2. 루프백, 로컬호스트

> 127.0.0.1

루프백(loopback), 로컬호스트(localhost), 127.0.0.1이라는 IP는 "나 자신에게서만 오는 요청만 받겠다"는 것을 의미한다.

127.0.0.1은 호스트 머신 자신을 가리키는 특수한 주소로 루프백 address라고 부른다.

이 IP 주소로 바인딩을 하면 호스트 머신/컨테이너 내부에서만 들어오는 요청만 받을 수 있고, 외부 인터페이스(eth0, wifi 등)를 통해 들어오는 요청은 버려진다.

```yml
ports:
	- "127.0.0.1:8081:8080"
```

이런식으로 바인딩을 하게 되면 호스트 머신 내부에서 8081로 접근했을 때만 8080으로 포워딩이 된다는 의미이다.

그러나 이렇게 설정이 되어 있어도, 접속이 불가능한 경우가 있을 수 있다. 만약에 어플리케이션 내부에서 8080번 포트를 127.0.0.1에만 바인딩을 해뒀다면, 아무리 호스트 머신 내부에서 8081번 포트로 찌른다고 한들 어플리케이션의 8080포트로 포워딩되지 않는다. 이렇게 된다면 사실상 컨테이너 내부의 어플리케이션에는 아무도 접근을 하지 못하므로 잘못된 설정이라고 할 수 있다.

<br>

## 3. 모든 인터페이스

> 0.0.0.0

"요청이 어느 경로로 들어오든 다 받겠다"는 의미를 가진다.

0.0.0.0의 경우 실제 존재하는 주소가 아니라, "해당 머신이 가진 모든 네트워크 인터페이스"를 의미하는 와일드카드이다.

그래서 보통 어플리케이션의 리스닝을 이야기할 때 IP를 같이 이야기하지 않는 이유는 일반적인 배포된 서비스에서는 모든 외부 요청을 받도록 해두기 때문이다.

그러니까 특수한 경우가 아니라면 앱은 모든 외부 요청에 대해서는 오픈해두고, 외부 경계에서 차단하는 방식을 택한다.

- Springboot, Express 등과 같은 프레임워크에서 IP를 생략하면 기본값은 0.0.0.0으로 되어 있다.

예를 들어, 컨테이너 환경에서는 어차피 컨테이너 자체가 격리돼 있고 외부 노출의 경우 ports를 통해 컨테이너 경계에서 바인딩을 통해 제어할 수 있기 때문에 앱 자체는 0.0.0.0으로 두는 것이다.

<br>

## 4. 정리

| 구분                        | 127.0.0.1                                | 0.0.0.0                |
| --------------------------- | ---------------------------------------- | ---------------------- |
| 의미                        | 나 자신에게서만                          | 어디에서 오든 다       |
| 호스트 내부에서 curl        | 접근 가능                                | 접근 가능              |
| 호스트 외부에서 접근        | 불가능                                   | 접근 가능              |
| 컨테이너 내부 앱에서 바인딩 | 앱에 접근이 불가능해지므로 권장하지 않음 | 권장 (기본값으로 사용) |
